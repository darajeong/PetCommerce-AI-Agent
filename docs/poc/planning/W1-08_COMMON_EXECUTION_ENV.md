## 3. 보안 및 인증 정보 관리

- API 키, 비밀번호, 인증 토큰은 GitHub에 업로드하지 않는다.
- 실제 인증 정보는 `.env` 등 Git에서 제외된 파일에 보관한다.
- `.gitignore`에 `.venv/`, `.env`, `__pycache__/` 등을 등록한다.
- 공유가 필요한 환경변수 이름은 `.env.example`에 작성하되 실제 값은 포함하지 않는다.
- 외부 플랫폼 접근 권한과 수집 가능 여부는 W1-07 점검 결과를 따른다.
- API 키나 인증 토큰이 실수로 커밋되면 즉시 해당 키를 폐기·재발급하고, 유출 범위를 확인한다. 파일이나 커밋 이력에서 삭제하는 것만으로는 안전하지 않다.
- W1-07에서 점검하는 외부 플랫폼 테스트 계정의 비밀번호·인증 토큰도 문서 및 실행 로그에 직접 기록하지 않는다.


## 4. Git 협업 및 리뷰 규칙

1. 최신 `main`에서 작업 브랜치를 생성한다.
2. 주 담당자는 담당 작업의 별도 브랜치에서 개발한다.
3. 주 담당자는 실행 결과를 확인하고 커밋 및 Push한 뒤 GitHub Pull Request를 생성한다.
4. WBS에 지정된 검토 담당자는 PR의 코드·문서·실행 결과를 확인한다.
5. 검토 담당자는 수정이 필요한 사항을 GitHub PR Review에 작성하고 주 담당자에게 리뷰 확인을 요청한다.
6. 주 담당자는 리뷰를 확인하여 필요한 코드·문서를 직접 수정하고, 기존 작업 브랜치에 커밋·Push하여 동일 PR에 반영한다.
7. 주 담당자가 리뷰를 반영한 뒤 동일 PR을 튜터님께 전달하고 승인 여부와 추가 피드백을 확인한다. 검토 담당자의 별도 재확인 단계는 두지 않는다.
8. 튜터님의 추가 수정 요청은 원래 주 담당자가 직접 반영하고 필요한 검증을 다시 수행한다. 수정 사항을 기존 작업 브랜치에 커밋·Push하여 동일 PR에 반영하고 튜터님의 최종 확인을 받는다.
9. 튜터님 승인 및 피드백 반영에 대한 최종 확정 후 팀 규칙에 따라 Merge한다.

검토 담당자는 직접 수정하지 않고 PR Review로 수정·보완 사항을 전달한다. 리뷰와 튜터님의 최종 승인 전에는 임의로 `main`에 병합하지 않는다.

### 6.3 팀원 재현 방법

**최초 실행 준비 (PR 브랜치 검토 시)**

아래 명령어는 W1-08 브랜치를 GitHub에 Push한 이후 사용할 수 있다.

```powershell
git clone https://github.com/darajeong/PetCommerce-AI-Agent.git

```

GitHub에서 PR이 Merge된 이후에는 `main`을 사용하므로 별도 브랜치 전환이 필요하지 않다.

가상환경 `.venv`는 최초 실행 시 한 번만 생성하면 된다. 이미 존재하면 생성 명령어를 생략하고 활성화한다.

저장소 최상위 폴더에서 실행한다.

**1. Windows PowerShell 가상환경 활성화**

```powershell

.\.venv\Scripts\Activate.ps1
```

macOS·Linux 환경은 다음 명령어를 사용한다.

```bash
python3 -m venv .venv
source .venv/bin/activate
```

**2. 샘플 실행 및 결과 저장**

**주의:** 아래 결과 저장 명령어는 작성자 E의 최초 실행 증빙 생성용이다. 검토 담당 B는 기존 JSON을 덮어쓰지 않도록 6.6절의 독립 재현 명령어를 사용한다. 실행 정책 오류 시 대체 명령어를 사용할 때도 결과 저장 경로를 별도로 지정한다.

```powershell
python docs/poc/samples/w1_08_smoke.py --output docs/poc/samples/W1-08_SMOKE_RESULT.json
```

**3. 저장된 JSON 검증**

```powershell
python -m json.tool docs/poc/samples/W1-08_SMOKE_RESULT.json
```

**기대 결과**

```json
{
  "poc_id": "W1-08",
  "test_type": "environment_smoke_test",
  "result": "pass",
  "judgement": "성공",
  "product_id": "mock-product-001",
  "data_type": "mock",
  "missing_fields": []
}
```

실제 출력에는 `executed_at`, `python_version`, `platform`도 포함된다.

실행 시각과 환경 정보는 실행자마다 달라질 수 있다. 공통 검증 항목이 동일하고 `result`가 `pass`이면 기본 테스트에 성공한 것으로 본다.

**PowerShell 실행 정책 오류가 발생할 경우**

가상환경 활성화 대신 다음처럼 전용 Python 실행 파일을 직접 사용할 수 있다.

```powershell
.\.venv\Scripts\python.exe docs/poc/samples/w1_08_smoke.py --output docs/poc/samples/W1-08_SMOKE_RESULT.json
```

#### 6.6.1 PR 검토 및 수정 절차

1. E 담당자가 W1-08 작업 브랜치에서 작업 및 검증 후 PR을 생성한다.
2. B 담당자는 PR의 코드·문서·실행 결과를 확인하고 PR 브랜치의 샘플을 별도 환경에서 한 번 독립 실행한다.
3. B 담당자는 6.7절의 항목에 따라 독립 재현 결과와 문제점, 수정이 필요한 사항을 GitHub PR Review에 작성하고 E 담당자에게 리뷰 확인을 요청한다.
4. E 담당자는 리뷰를 확인하고 필요한 코드·문서를 직접 수정한다. B 담당자가 전달한 검증 기록을 6.7절에 반영하고 기존 W1-08 작업 브랜치에 커밋·Push하여 동일 PR에 반영한다.
5. 코드 또는 실행 절차를 수정했다면 E 담당자가 변경된 최종 버전으로 직접 다시 실행하여 결과를 확인하고 6.7절과 PR 코멘트에 변경 내용과 재실행 결과를 기록한다. B 담당자의 재확인 단계는 두지 않는다.
6. 동일 PR을 튜터님께 전달하고 승인 여부와 추가 피드백을 확인한다.
7. 튜터님의 추가 수정 요청은 원래 업무 담당자인 E가 직접 반영한다. 필요한 검증을 다시 수행하고 수정 사항과 검증 기록을 기존 W1-08 작업 브랜치에 커밋·Push하여 동일 PR에 반영한 뒤 튜터님의 최종 확인을 받는다.
8. 튜터님 승인 및 피드백 반영에 대한 최종 확정 후 팀 규칙에 따라 Merge하며 별도의 검토용 PR은 생성하지 않는다.

검토자는 기존 E 담당자의 실행 증빙 JSON을 유지하며, 독립 재현 결과는 PR Review로 전달하고 E 담당자가 6.7절에 별도로 기록한다.

B 담당자는 기존 PR 브랜치의 코드·문서를 직접 수정하거나 커밋·Push하지 않는다. 수정과 검증 기록 반영은 E 담당자가 수행한다.

B 담당자의 독립 재현 이후 샘플 코드나 실행 절차가 변경되면 E 담당자가 최종 버전을 직접 재실행하고, 변경 내용을 PR 코멘트와 6.7절에 명시한다.

독립 재현 항목은 B 담당자의 PR Review 결과를, 수정·반영 항목은 E 담당자의 작업 내용을, 튜터님 관련 항목은 튜터님의 확인 내용을 기록한다.

B 담당자는 별도 경로에 저장한 JSON에서 `executed_at`, `python_version`, `platform`, `result`를 확인하고, 위 항목에 따른 독립 재현 결과와 문제점을 PR Review로 전달한다. E 담당자는 전달받은 검증 기록과 수정 내용을 이 절에 반영한다.

코드나 실행 절차를 변경하지 않았다면 'E 담당자의 최종 버전 재실행 결과' 행에 '변경 없음'으로 기록한다.

튜터님의 추가 피드백은 E 담당자가 직접 반영하고 필요한 재검증 결과와 튜터님의 최종 확인을 기록한다. 추가 피드백이 없다면 해당 항목에 '추가 피드백 없음'으로 기록한다.

독립 재현이 완료되기 전까지 W1-08을 최종 완료로 처리하지 않는다.

## 7. 연계 및 미확정 사항
