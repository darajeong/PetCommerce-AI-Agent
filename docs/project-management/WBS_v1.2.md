## 프로젝트 운영 원칙

- 작은 단위로 나누어 실제 실행하고, 성공 여부와 결과 품질을 증빙으로 판단한다.
- 각 PoC에는 목표, 입력, 절차, 소스 또는 지시문, 결과, 실패 원인과 다음 결정을 기록한다.
- 같은 절차를 다른 사람이 재현할 수 있어야 한다.
- 실패 시 원인과 대체 방법을 기록한다.
- 외부 실행은 관리자 승인 전후를 구분한다.
- W1-W5에서 검증된 기능만 W6 이후 제품 소스로 전환한다.

- W1부터 5인 배분을 적용하며 기존 13주 일정, WBS ID, 필수 PoC 8개와 완료 기준은 유지한다.
- 각 작업은 주 담당자 1명이 실행·기록하고 다른 팀원 1명이 검토·승인한다. 주요 결정도 지정된 검토 담당자 1명의 승인으로 완료한다.
- 주 담당자와 검토 담당자는 같은 사람이 될 수 없다.

### 범위별 검증 원칙

- **필수 PoC:** 실제 상품 3건 이상, 반복 실행, 예외 처리, 결과 품질과 비용을 확인한다.
- **확장 PoC:** 대표 사례 1건 또는 Mock 데이터로 계산·생성 가능성과 입출력 계약을 확인한다.
- **외부 연동:** 실제 등록·발송 성공을 필수 기준으로 두지 않는다. 권한이나 정책상 불가능하면 API 호출 직전 데이터, 업로드 파일, 필수 필드 검사와 수동 절차까지 검증한다.
- **공통 기록:** 실제 연동 범위, Mock 사용 여부, 미검증 범위, 수동 단계, 제한 사항과 후속 착수 조건을 기록한다.
- **제품화 원칙:** 확장 기능은 W5에서 조건부 제품화로 승인되고 필수 MVP 일정에 영향이 없을 때만 착수한다.

## 기술 아키텍처 및 Agent 통신 구조

### 적용 기술 스택

본 프로젝트는 다음 기술 스택을 기준으로 PoC와 MVP를 개발한다.

- **Frontend:** React + TypeScript
- **Backend:** Python + FastAPI
- **Agent:** LangGraph 기반 Python 워크플로
- **Database:** PostgreSQL
- **비동기 실행:** Celery + Redis
- **AI:** 이미지와 텍스트를 처리하는 멀티모달 LLM API
- **배포:** Docker Compose 기반

W1-W5에서는 실제 기술 환경에서 각 구성 요소의 적용 가능성과 제한 사항을 확인한다. W5 종료 시 PoC 결과를 바탕으로 세부 구성을 최종 확정하고, W6부터 위 기술 스택으로 MVP를 구현한다.

### 전체 시스템 실행 구조

`React → FastAPI → E04 오케스트레이터 → Celery·Redis → A/B/C Agent → PostgreSQL → FastAPI → React`

- React는 상품 입력, 실행 상태, 분석 결과와 관리자 승인 화면을 제공한다.
- FastAPI는 Frontend 요청을 검증해 E04에 전달하고 실행 상태와 최종 결과를 반환한다.
- E04는 LangGraph 기반으로 Agent 실행 순서, 병렬 실행, 상태, 오류, 재시도와 관리자 승인을 관리한다.
- Celery와 Redis는 수집·분석·콘텐츠 생성처럼 시간이 오래 걸리는 작업을 비동기로 실행하고 작업 상태를 전달한다.
- A/B/C Agent는 상품 수집·번역, 상품 분석·점수화와 판매 콘텐츠 생성을 담당한다.
- PostgreSQL은 상품 원본, Agent 결과, 실행 상태, 오류, 근거, 결과 버전과 승인 이력을 저장한다.
- D·E Agent는 W5에서 제품화 또는 조건부 제품화로 승인된 기능만 W11-W12에 연결한다.

### 핵심 Agent 실행 순서

1. 사용자가 React 화면에서 상품 URL 또는 상품 정보를 입력한다.
2. FastAPI가 요청을 검증하고 실행 ID와 상품 ID를 생성한다.
3. E04가 A02 상품 정보 수집을 실행한다.
4. A03이 수집 결과를 번역하고 가격·크기·무게·옵션을 정규화한다.
5. A02와 A03의 결과가 준비되면 B01·B02·B04를 병렬로 실행한다.
6. B05가 B01·B02·B04의 분석 결과를 이용해 상품 점수를 계산한다.
7. C02가 상품 정보, 분석 결과와 점수를 이용해 상세페이지를 생성한다.
8. 관리자가 결과와 근거를 확인하고 승인하거나 반려한다.
9. PostgreSQL에 결과, 실행 상태, 오류, 근거와 승인 이력을 저장한다.
10. FastAPI가 최종 결과를 React 화면에 반환한다.

### Agent 공통 데이터 구조

모든 Agent는 동일한 상품 ID와 실행 ID를 사용하며 다음 공통 데이터를 전달받거나 저장한다.

| 데이터 구분 | 주요 내용 | 생성·사용 Agent |
|---|---|---|
| 실행 정보 | 실행 ID, 실행 시각, 현재 상태, 데이터 버전 | E04 및 전체 Agent |
| 상품 식별 정보 | 상품 ID, 원본 URL, 플랫폼 | A02 및 전체 Agent |
| 상품 원본 정보 | 상품명, 설명, 가격, 통화, 옵션, 규격, 크기, 무게, 소재 | A02 |
| 이미지·리뷰 | 이미지 URL, 이미지 번호, 리뷰 원문, 평점, 출처 | A02, B01, B02 |
| 번역·정규화 | 한국어 상품명, 번역 설명, 원화 가격, 통일된 크기·무게·옵션 | A03 |
| 상품 분석 | 특징, 장단점, 반복 불만, 대형견 적합성, 분석 근거 | B01, B02, B04 |
| 상품 점수 | 항목별 점수, 총점, 감점 사유, 추천 근거 | B05 |
| 생성 콘텐츠 | 상세페이지, 주의사항, FAQ, 문장별 근거 | C02 |
| 실행 결과 | 성공 여부, 경고, 오류, 재시도 횟수, 처리 시간 | 전체 Agent |
| 승인 정보 | 승인 상태, 승인자, 승인·반려 사유, 승인 시각 | E04 및 관리자 화면 |

A02는 상품명, 가격, 옵션, 규격, 이미지, 리뷰와 출처를 공통 구조로 저장한다. B01은 이미지와 상품 설명, B02는 리뷰 원문과 평점, B04는 규격·크기·무게·소재·리뷰를 같은 공통 데이터에서 사용한다. 각 Agent는 상품 원본을 직접 덮어쓰지 않고 자신의 결과 영역에 결과와 근거를 추가한다.

### Agent 공통 입력·출력·오류 규칙

#### 공통 입력

- 실행 ID와 상품 ID
- 실행할 Agent ID
- 입력 데이터 버전
- 이전 단계의 결과
- 실제 데이터·테스트 데이터·Mock 데이터 구분

#### 공통 출력

- 실행 ID, 상품 ID와 실행한 Agent ID
- 실행 상태와 처리 결과
- 결과의 원본 근거
- 경고와 사람의 확인이 필요한 사항
- 오류 정보와 재시도 횟수
- 결과 버전
- 시작 시각과 종료 시각

#### 공통 실행 상태

- 대기
- 실행 중
- 성공
- 부분 성공
- 실패
- 검토 필요
- 승인 대기
- 승인 완료
- 반려
- 보류

#### 오류 기록 항목

- 오류가 발생한 Agent와 단계
- 오류 종류와 원인
- 자동 재시도 가능 여부와 실제 재시도 횟수
- 수동 입력 또는 Mock 데이터 대체 가능 여부
- 다음에 수행할 작업

#### 오류 처리 원칙

- 일시적인 네트워크·API 오류는 최대 2회 자동 재시도한다.
- 로그인·전화 인증·접근 제한은 자동 재시도하지 않고 사람의 확인을 요청한다.
- 필수 정보가 없으면 누락 사유를 저장하고 수동 입력을 요청한다.
- A02 또는 A03이 실패하면 후속 자동 실행을 중단하고 대체 경로를 안내한다.
- B01·B02·B04 중 일부가 실패하면 성공 결과를 보존하고 `부분 성공`으로 기록한다.
- 재실행할 때 기존 결과를 덮어쓰지 않고 새로운 결과 버전을 저장한다.

## 프로젝트 실행 가드레일

### 주의사항

- PoC 단계에서는 완성품을 만들지 않는다. 실행 상태는 `완료·보완·실패·보류`, 기술 판정은 `기술 검증 완료·추가 검증 필요·외부 제약·검증 실패`로 구분해 근거를 기록한다.
- 타오바오, 알리바바, 네이버, 쿠팡 및 광고 플랫폼의 테스트 계정과 접근 권한은 W1에 확보한다.
- 법규·인증·안전성 결과는 AI가 최종 확정하지 않는다. AI는 검토 자료를 작성하고, 최종 판단은 사람이 수행한다.
- W9와 W10은 휴일 주간이므로 계획된 핵심 작업만 진행하며 새로운 외부 연동이나 대규모 기능을 추가하지 않는다.
- 통합 작업을 W13까지 미루지 않는다. 매주 결과를 공통 저장소에 반영하고 다른 기능과의 연결 여부를 확인한다.

### 주간 운영 규칙

1. 매주 시작할 때 담당자, 입력 데이터, 의존 작업과 완료 기준을 확정한다.
2. 주 2~3회 진행 상황과 결과를 함께 검토한다.
3. 한 작업이 1일 이상 막히면 혼자 계속 진행하지 않고 원인을 공유해 대체 방법을 결정한다.
4. 매주 금요일 실제 실행 화면, 산출물 또는 테스트 결과를 시연한다.
5. 미완료 작업은 자동으로 다음 주에 이월하지 않는다. 원인과 중요도를 검토해 `보완·보류·제외` 중 하나로 결정한다.

## PoC 실행 순서

1. 검증 질문을 한 문장으로 정의한다.
2. 성공 기준과 필수 산출물을 먼저 정한다.
3. 가장 작은 입력과 절차로 실제 실행한다.
4. 입력, 소스, 화면, 결과와 오류를 저장한다.
5. 실행 상태와 기술 판정을 분리해 기록한다.
6. Go, Conditional Go, No-Go, Hold 중 하나를 제안하고 제품화 상태를 함께 기록한다.

## PoC 정량 판정 기준

모든 PoC의 성공 기준은 **검증 수량 + 허용 오류 + 필수 증빙 + 실패 시 처리**를 포함한다. 아래 수치는 초기 기준이며 W1에서 실제 기술 환경과 검증 가능성을 확인한 뒤 주 담당자와 검토 담당자가 최종 승인한다.

### 공통 검증 수량

- 필수 PoC: 서로 다른 실제 상품 3개
- 확장 PoC: 대표 사례 최소 1개
- 동일 입력 반복 검증: 상품별 3회
- 리뷰 분석: 상품별 최소 20개 권장. 20개 미만이면 확보 가능한 리뷰를 모두 사용하고 부족 사유를 기록한다.
- 이미지 분석: 상품별 최소 5장 권장. 5장 미만이면 확보 가능한 이미지를 모두 사용하고 부족 사유를 기록한다.
- 통합 실행: 서로 다른 상품 3개

### 공통 필수 데이터와 누락 사유

다음 항목은 값을 저장하거나 누락 사유를 반드시 기록한다.

- 원본 URL, 플랫폼, 상품명, 가격과 통화
- 옵션, 규격, 크기, 무게와 소재
- 대표 이미지, 상세 설명과 리뷰
- 공급업체, 수집 시각과 데이터 출처

누락 사유는 `원본 정보 없음·로그인 필요·접근 제한·수집 실패·수동 확인 필요` 중 하나로 기록한다.

### 공통 결과 기준

- 모든 실행에 실행 ID와 상품 ID가 존재한다.
- 실제 데이터와 Mock 데이터를 명확히 구분한다.
- 주요 결과의 원본 근거 연결률은 100%로 한다.
- 원본에 없는 상품 사양·수치·인증·효능 주장은 0건이어야 한다.
- 실패한 실행도 실패 단계·원인·다음 행동을 100% 기록한다.
- 필수 산출물 누락은 0건이어야 한다.
- 주 담당자가 아닌 팀원 1명 이상이 같은 절차를 재현한다.
- 모든 실행은 `성공·부분 성공·실패·보류` 중 하나로 판정한다.

## 난이도·공수·검토 배정 기준

- **MD(Man-Day, 인일):** 한 사람이 하루 약 8시간 동안 수행하는 작업량이다. `0.25MD`는 약 2시간, `0.5MD`는 약 4시간이다.
- **예상 공수:** 주 담당자의 실행·기록 공수와 검토 담당자의 검토 공수를 `주 담당 MD + 검토 MD`로 구분한다.
- **난이도 하:** 문서화, 기준 정리, 단순 검토처럼 기술적 불확실성이 낮은 작업이다.
- **난이도 중:** AI 처리, 데이터 변환, 화면·콘텐츠 구현처럼 검증과 예외 처리가 필요한 작업이다.
- **난이도 상:** 외부 플랫폼, 인증, 공통 데이터·API, Agent 통합, 오류 복구, 보안·배포처럼 실패 영향과 기술적 불확실성이 큰 작업이다.
- **검토 분야:** A는 상품 원본·수집·번역, B는 AI 분석·수치·점수, C는 콘텐츠·화면·사용성, D는 외부 채널·마케팅·성과, E는 API·DB·E04·통합·QA·배포 검토를 우선 담당한다.
- 주 담당자와 검토 담당자는 동일인으로 지정하지 않는다. 분야 적합성을 우선하되 같은 주의 검토 공수가 한 사람에게 과도하게 몰리지 않도록 배분한다.
- 개인별 주간 총공수는 주 담당 공수와 검토 공수를 합산해 비교한다. `4MD 이하`를 계획 목표로 삼고 초과 주차는 우선순위 조정, 범위 축소 또는 후속 이동을 검토한다.

#### W5 Go / Conditional Go / No-Go 판정 체계

| W5 판정 | 제품화 상태 | 의미 | 일정 처리 |
|---|---|---|---|
| Go | MVP 제품화 | W5 검증을 통과해 실제 운영 가능한 기능으로 개발한다. | W6-W12 확정 백로그에 반영 |
| Conditional Go | 조건부 제품화 | 보완 조건과 필수 MVP 일정 보호 조건이 충족될 때 개발한다. | 확정 일정과 분리하고 담당자·기한·착수 게이트 지정 |
| No-Go | 재검증·제외 | 현재 기술·정책·품질 조건에서 이번 MVP로 구현하기 어렵다. | 제외 사유와 재검증 조건을 기록하고 확정 일정에서 제거 |
| Hold | PoC 완료·제품화 보류 | 외부 권한·실제 데이터·법적 검토 등 선행 조건이 부족하다. | 후속 백로그로 이관하고 재판정 시점 기록 |

> W5 판정은 제품화 범위를 결정하는 공식 게이트다. Go 기능만 확정 개발 범위에 포함하며, Conditional Go는 명시된 착수 조건을 충족하고 필수 MVP 일정에 영향이 없을 때만 진행한다.

- **품질:** 실제 화면, 콘텐츠 또는 보고서로 사용할 수 있는 수준인가?
- **예외:** 계정, 누락, 차단, AI 오류와 외부 연동 실패를 어떻게 처리하는가?
- **비용:** 처리 시간과 호출 비용이 MVP에서 감당 가능한가?
- **범위:** 필수·확장 구분과 실제·Mock 검증 수준이 지켜졌는가?
- **결정:** Go, Conditional Go, No-Go, Hold 중 어떤 판정이며 다음 행동은 무엇인가?
