### 범위별 검증 원칙

- **필수 PoC:** 실제 상품 3건 이상, 반복 실행, 예외 처리, 결과 품질과 비용을 확인한다.

- **외부 연동:** 실제 등록·발송 성공을 필수 기준으로 두지 않는다. 권한이나 정책상 불가능하면 API 호출 직전 데이터, 업로드 파일, 필수 필드 검사와 수동 절차까지 검증한다.
- **공통 기록:** 실제 연동 범위, Mock 사용 여부, 미검증 범위, 수동 단계, 제한 사항과 후속 착수 조건을 기록한다.
- **제품화 원칙:** 확장 기능은 W5에서 조건부 제품화로 승인되고 필수 MVP 일정에 영향이 없을 때만 착수한다.

## 프로젝트 실행 가드레일

### 주의사항

- PoC 단계에서는 완성품을 만들지 않는다. 실행 상태는 `완료·보완·실패·보류`, 기술 판정은 `기술 검증 완료·추가 검증 필요·외부 제약·검증 실패`로 구분해 근거를 기록한다.
- 타오바오, 알리바바, 네이버, 쿠팡 및 광고 플랫폼의 테스트 계정과 접근 권한은 W1에 확보한다.
- 법규·인증·안전성 결과는 AI가 최종 확정하지 않는다. AI는 검토 자료를 작성하고, 최종 판단은 사람이 수행한다.
- W9와 W10은 휴일 주간이므로 계획된 핵심 작업만 진행하며 새로운 외부 연동이나 대규모 기능을 추가하지 않는다.
- 통합 작업을 W13까지 미루지 않는다. 매주 결과를 공통 저장소에 반영하고 다른 기능과의 연결 여부를 확인한다.

### 주간 운영 규칙

1. 매주 시작할 때 담당자, 입력 데이터, 의존 작업과 완료 기준을 확정한다.
2. 주 2~3회 진행 상황과 결과를 함께 검토한다.
3. 한 작업이 1일 이상 막히면 혼자 계속 진행하지 않고 원인을 공유해 대체 방법을 결정한다.
4. 매주 금요일 실제 실행 화면, 산출물 또는 테스트 결과를 시연한다.
5. 미완료 작업은 자동으로 다음 주에 이월하지 않는다. 원인과 중요도를 검토해 `보완·보류·제외` 중 하나로 결정한다.
6. 새로운 기능을 추가하려면 기존 일정과 MVP 범위에 미치는 영향을 먼저 확인한다.

## PoC 실행 순서

1. 검증 질문을 한 문장으로 정의한다.
2. 성공 기준과 필수 산출물을 먼저 정한다.
3. 가장 작은 입력과 절차로 실제 실행한다.
4. 입력, 소스, 화면, 결과와 오류를 저장한다.
5. 실행 상태와 기술 판정을 분리해 기록한다.
6. MVP 제품화, 조건부 제품화, PoC 완료·제품화 보류, 재검증·제외 중 하나를 제안한다.

## PoC 정량 판정 기준

모든 PoC의 성공 기준은 **검증 수량 + 허용 오류 + 필수 증빙 + 실패 시 처리**를 포함한다. 아래 수치는 초기 기준이며 W1에서 실제 기술 환경과 검증 가능성을 확인한 뒤 팀원 3명이 최종 승인한다.

### 공통 검증 수량

- 필수 PoC: 서로 다른 실제 상품 3개
- 확장 PoC: 대표 사례 최소 1개
- 동일 입력 반복 검증: 상품별 3회
- 리뷰 분석: 상품별 최소 20개 권장. 20개 미만이면 확보 가능한 리뷰를 모두 사용하고 부족 사유를 기록한다.
- 이미지 분석: 상품별 최소 5장 권장. 5장 미만이면 확보 가능한 이미지를 모두 사용하고 부족 사유를 기록한다.
- 통합 실행: 서로 다른 상품 3개

### 공통 필수 데이터와 누락 사유

다음 항목은 값을 저장하거나 누락 사유를 반드시 기록한다.

- 원본 URL, 플랫폼, 상품명, 가격과 통화
- 옵션, 규격, 크기, 무게와 소재
- 대표 이미지, 상세 설명과 리뷰
- 공급업체, 수집 시각과 데이터 출처

누락 사유는 `원본 정보 없음·로그인 필요·접근 제한·수집 실패·수동 확인 필요` 중 하나로 기록한다.

### 공통 결과 기준

- 모든 실행에 실행 ID와 상품 ID가 존재한다.
- 실제 데이터와 Mock 데이터를 명확히 구분한다.
- 주요 결과의 원본 근거 연결률은 100%로 한다.
- 원본에 없는 상품 사양·수치·인증·효능 주장은 0건이어야 한다.
- 실패한 실행도 실패 단계·원인·다음 행동을 100% 기록한다.
- 필수 산출물 누락은 0건이어야 한다.
- 주 담당자가 아닌 팀원 1명 이상이 같은 절차를 재현한다.
- 모든 실행은 `성공·부분 성공·실패·보류` 중 하나로 판정한다.

## 난이도·공수·검토 배정 기준

- **MD(Man-Day, 인일):** 한 사람이 하루 약 8시간 동안 수행하는 작업량이다. `0.25MD`는 약 2시간, `0.5MD`는 약 4시간이다.
- **예상 공수:** 주 담당자의 실행·기록 공수와 검토 담당자의 검토 공수를 `주 담당 MD + 검토 MD`로 구분한다.
- **난이도 하:** 문서화, 기준 정리, 단순 검토처럼 기술적 불확실성이 낮은 작업이다.
- **난이도 중:** AI 처리, 데이터 변환, 화면·콘텐츠 구현처럼 검증과 예외 처리가 필요한 작업이다.
- **난이도 상:** 외부 플랫폼, 인증, 공통 데이터·API, Agent 통합, 오류 복구, 보안·배포처럼 실패 영향과 기술적 불확실성이 큰 작업이다.
- **검토 분야:** A는 통합·외부 연동·실행 흐름, B는 데이터·API·품질·수치 검증, C는 화면·콘텐츠·승인·사용성 검토를 우선 담당한다.
- 주 담당자와 검토 담당자는 동일인으로 지정하지 않는다. 분야 적합성을 우선하되 같은 주의 검토 공수가 한 사람에게 과도하게 몰리지 않도록 배분한다.
- 개인별 주간 총공수는 주 담당 공수와 검토 공수를 합산해 비교한다. `4MD 이하`를 계획 목표로 삼고 초과 주차는 우선순위 조정, 범위 축소 또는 후속 이동을 검토한다.
